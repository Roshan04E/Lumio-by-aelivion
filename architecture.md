## Product Direction

Orreris is a browser-first video editor for short-form creators.

It should feel simple for normal users, but familiar enough for Premiere Pro and After Effects users:

```text
Assets -> Timeline -> Project Graph -> Render Manifest -> Renderer Adapter
                                             -> Web preview
                                             -> Browser export
                                             -> Local desktop render
                                             -> Cloud worker render
```

The render manifest is the product contract. Every renderer should consume deterministic data so preview, export, local render, and cloud render stay aligned.

## Two Usage Paths

Orreris must support two different user realities.

### Path 1: Free Prompt Bridge

For users who cannot pay for integrated AI:

```text
User opens a tool
  -> Orreris generates a precise prompt/schema
  -> user copies it into their own chat agent
  -> chat agent returns transcript/captions/JSON/etc.
  -> user pastes the result back into Orreris
  -> Orreris validates it and applies editable timeline data
```

This path must stay first-class, not treated like a hack. It is important for students, middle-class creators, low-budget editors, and users who already have access to free chat tools.

### Path 2: Integrated AI

For users who want convenience:

```text
User asks Orreris chat
  -> AI chooses a tool
  -> AI fills params
  -> user confirms
  -> adapter runs browser/cloud/local work
  -> artifacts become editable timeline data
```

The same tool capability registry powers both paths.

## Future Pricing Direction

Do not implement pricing yet.

Keep these future modes in mind:

- Free/manual: user copies prompts to external AI and pastes output back.
- Subscription: integrated AI/chat convenience and higher limits.
- Pay per output: one-off render/transcription/masking jobs.

During product build:

- credits are metadata only
- no subscription dependency
- no hard credit blockers
- all tool results must remain editable

[x] **Local export of graphics fixed**: vector graphics resolve to `data:image/svg+xml` URLs, but `createImageBitmap` cannot rasterize an SVG blob without a layout engine — it throws in the DOM-less export Worker and fails on Firefox/Safari even on the main thread. [x] **Animated icon packs (line-md, …) now ANIMATE instead of freezing**: previously `settleSvgAnimations` baked each animation's FINAL value and stripped the SMIL at import + bake — a deliberate workaround, since those icons hide their base state and draw themselves in, so a static raster of the base painted nothing. Live playback replaces the freeze. The unifying primitive is the **SMIL deep-link**: an `<img>` whose animations are rewritten to `begin="-(T-ε)s" end="εs" fill="freeze"` renders frame T and HOLDS it — deterministic under Remotion's frozen clock AND capturable on the main thread. The freeze is load-bearing, not decoration: `begin` alone renders frame T only at document time 0, and an `<img>`'s SVG clock runs from load, so the capture delay silently adds to the phase (the export's parallel rasterize skewed later frames by a large fraction of a cycle — see project-tracker/export.md v6). `ε` must be > 0; `end="0s"` makes Chrome render the base state. Shared primitives (`layer-graphic.ts`): `getGraphicAnimationCycleSeconds` (memoized), `graphicIsAnimated`, `shiftSvgSmilBegin`, `graphicToAnimatedDataUrl`, and `graphicAnimationFrame` — the ONE frame-selection math all three renderers call, keyed on CLIP-LOCAL time and looping the natural cycle for the clip's duration. `graphicToDataUrl` (settled) stays as the static/non-animated bake. No persisted `LayerGraphic` field — animation is derived from the SVG, so no migration.
  - **Preview** (`WebglMediaLayer`): pre-bakes the cycle to frame bitmaps once (512px, re-baked on recolor via `graphicBakeSig`); `snapshot()` selects a frame against `getLivePlaybackTime()` and versions it `epoch*100000+frameIndex` so the single-ctx compositor re-uploads on frame change / recolor but skips within a held frame. No per-frame SVG decode on the hot path.
  - **Local export**: `buildSourceUrlMap` emits one deep-linked frame URL per cycle index (`animation` on `SourceUrlMap`), `local-export` rasterizes them to PNG main-thread, `createAnimatedGraphicSource` serves them — so the Worker needs no DOM. `scene-frame-compositor` now passes CLIP-LOCAL time for graphics (was hardcoded `sourceTime = 0`).
  - **Remotion**: manifest carries `graphic` + `graphicAnimationCycleSeconds`; `ImageGrabber` rebuilds the deep-linked `src` per frame from its Sequence-local `useCurrentFrame()` (`delayRender` already blocks until decoded). The matte layer explicitly drops the graphic fields or it would decode the graphic as its own matte.

[x] **Loop control honors the icon author, with per-layer overrides** (`LayerGraphic.animation`, no migration — absent = author's intent): the SVG itself declares the intent, so `resolveGraphicAnimation` reads it — `repeatCount="indefinite"` (spinner) → loop; `fill="freeze"` one-shot (line-md draw-in) → play once and HOLD the completed frame. `shiftSvgSmilBegin` therefore does NOT touch `repeatCount`/`repeatDur` (forcing `indefinite` overrode `fill="freeze"` and looped draw-ins against their author) and SHIFTS the author's own `begin` delay rather than clobbering it, so staggered icons keep their choreography. The Graphic inspector panel adds **Loop** (Auto / Play once / Loop infinite) + **Duration** (time-scales playback: `playDurationSeconds` is the SELECTION domain, `naturalCycleSeconds` the SVG deep-link domain). Bake times differ per mode: looping spreads frames over `[0, cycle)` so the wrap is seamless; one-shot spreads over `[0, cycle]` so the last frame is the completed state.
  - Gotcha (caught by `graphic:render`): the one-shot final frame must deep-link a hair INSIDE the active end — at exactly `begin+dur` Chrome rendered the BASE state (a blank icon at the very frame the clip holds), and `fill="remove"` would revert there by spec.

[x] **Keyframeable animation** — one PHASE (cycles completed) that every renderer selects frames from, resolved in precedence order by `graphicAnimationPhase`:
  1. **`graphicProgress` keys** (cycles; 1 = one full cycle) — they ARE the phase, so hold / reverse / ease / N-cycles all fall out for free, and they outrank everything below. No base storage (a lone static value would just freeze it), so a scrub always drops a key.
  2. **`graphicDuration` keys** — a speed ramp. The phase is the exact **integral** ∫₀ᵗ 1/duration(u) du, mirroring `integrateRamp`'s model (linear segments + edge-hold) but closing to `(1/k)·ln(d(t)/d₀)` per segment because the integrand is a hyperbola, not a line. Evaluating `t % duration(t)` directly would make the animation JUMP at every duration change — the integral is what keeps the phase continuous.
  3. **Static** Loop + Duration (above).
  Both rows use the canonical `NumberControl` + `KeyframeButtons` affordance via new generic `applyLayerPropertyValueAtTime` / `toggleLayerPropertyKeyframe` / … helpers in `keyframeUtils.ts` (layer-scope V2 numerics whose base lives outside `layer.content` — the `content.*` helpers generalized). Keyframe times are LAYER-LOCAL (the V2 convention: `evaluateTimelineTransform` evaluates at `timeSeconds - startSeconds`), which is also why they survive a work-area in-point shift untouched. `frameCount` comes from the SLOWEST cycle the clip ever plays, so a stretched animation still bakes enough frames. Loop mode is deliberately NOT keyframeable — it's a mode, not a value; progress keys supersede it anyway.
  - Preview reads the plan through a REF (`graphicPlanRef`), not the compositor's `snapshot()` closure, which would otherwise pin the plan + clip start from the render its effect ran in — live keyframe edits and clip drags would never reach frame selection.

They evaluate through the SHARED resolver, not the raw keyframe track — the phase is only sometimes a track (Progress keys); otherwise it's the static cycle or a ramp's integral, which no track holds, and a track-read lane would draw a flat 0 lie. Ranges/steps mirror the inspector rows so both surfaces clamp alike.

## Orreris AI Operating System — Phased Roadmap

Vision (`AI_ARCHITECTURE.md`): Orreris is a professional editor with an **AI operating system on top** — "Claude Code for video editing". AI never mutates the timeline directly. It *plans → selects registered tools/actions → previews → asks when it matters → executes through an approved registry*, leaving everything editable and undoable. The editor stays fully usable without AI.

```text
User → AI Chat Panel → Planner → Capability Registry → Plan Review
     → Executor → Timeline Action Registry → patches → Undo Stack → Editor Timeline
```

Foundational rule: the **Timeline Action Registry is the only approved mechanism for AI timeline mutation.** AI may only invoke registered, validated, reversible actions that *wrap* the existing pure ops — never touch `TimelineLayer`/effects/keyframes directly, never touch rendering (manifest stays the contract; web↔Remotion parity preserved).

### Provider Gateway — multi-model failover (free-first, internet-scale)

Decision (validated for an indie launch): don't bind the brain to one provider. Behind the *unchanged* `/api/ai/plan` route, swap the single LLM call for a **config-driven pool with automatic failover**. The full AI spine (PlannerProvider, slice payload, **registry validation of every step**, Plan Review, Executor→patches→Undo, permission modes, memory, analytics, interactive clarify/tool loop) is untouched — only the server-side brain grows. Keys stay server-side (multi-user safe). Reasoning models are weaker than Claude, but **registry validation + deterministic floor** guarantee safety/precision regardless of model quality.

Failover chain (priority order; a provider is skipped when its key is absent or it's in cooldown after a 429/503/5xx/timeout):
```text
Cerebras → Groq → OpenRouter → Gemini → Claude Sonnet (paid, opt-in) → Deterministic planner (always-free floor)
```
All pool members are **OpenAI-compatible** (`POST /v1/chat/completions`) → one adapter, model IDs env-overridable (free tiers drift — config, not code). Free RPD is small, so multi-user needs: per-IP rate limit + short-TTL plan cache (both P1), BYO-key (P2).
