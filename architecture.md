# Orreris Architecture And Progress Tracker

Last updated: 2026-07-27

This file is the working architecture and product tracker. Keep it crisp:

- what is already shipped
- what is intentionally deferred
- what we are building next
- what future business/AI paths must not be forgotten

## Product Direction

Orreris is a browser-first video editor for short-form creators.

It should feel simple for normal users, but familiar enough for Premiere Pro and After Effects users:

```text
Assets -> Timeline -> Project Graph -> Render Manifest -> Renderer Adapter
                                             -> Web preview
                                             -> Browser export
                                             -> Local desktop render
                                             -> Cloud worker render
```

The render manifest is the product contract. Every renderer should consume deterministic data so preview, export, local render, and cloud render stay aligned.

## Two Usage Paths

Orreris must support two different user realities.

### Path 1: Free Prompt Bridge

For users who cannot pay for integrated AI:

```text
User opens a tool
  -> Orreris generates a precise prompt/schema
  -> user copies it into their own chat agent
  -> chat agent returns transcript/captions/JSON/etc.
  -> user pastes the result back into Orreris
  -> Orreris validates it and applies editable timeline data
```

This path must stay first-class, not treated like a hack. It is important for students, middle-class creators, low-budget editors, and users who already have access to free chat tools.

### Path 2: Integrated AI

For users who want convenience:

```text
User asks Orreris chat
  -> AI chooses a tool
  -> AI fills params
  -> user confirms
  -> adapter runs browser/cloud/local work
  -> artifacts become editable timeline data
```

The same tool capability registry powers both paths.

## Future Pricing Direction

Do not implement pricing yet.

Keep these future modes in mind:

- Free/manual: user copies prompts to external AI and pastes output back.
- Subscription: integrated AI/chat convenience and higher limits.
- Pay per output: one-off render/transcription/masking jobs.

During product build:

- credits are metadata only
- no subscription dependency
- no hard credit blockers
- all tool results must remain editable

## Current Shipped Foundation

[x] **Flarex — the unified `color` node (Resolve's corrector model) (2026-07-27).** One node carrying the whole grade toolset — primary correction, wheels, curves, hue/sat, qualifier, LUT, look, plus vignette/grain — with the Resolve rule that you chain nodes when you need a different **mask**, not a different tool (which is exactly what the `mask` input socket already means). The seven atomic colour nodes stay for precise Fusion-style graphs; `color` is the pinned default. **It is strictly cheaper than the equivalent chain, not just tidier:** the grade engine bakes an effect LIST into ONE pipeline (one 3D LUT, one pass), so every stage costs what one stage costs — and unlike a chain it cannot hit the P1 coalescing refusals, which open a nested render target whenever a stage type REPEATS (Wheels → Curves → Wheels is two nests as three nodes, one pipeline as one node). **No second colour path exists:** `lowerColorNode` was generalized from one effect to a LIST, so both families share one body, one set of param conventions (identical names/scales/JSON payload shapes) and one set of inspector editors. The gate that pins this is `UNIFIED == CHAIN: identical compiled pipeline` — one Color node and the equivalent 6-node chain must compile to a byte-identical `ColorPipeline`, which makes the stage ORDER (primary → wheels → curves → hue/sat → qualifier → LUT → look) a tested contract rather than a comment. Two deliberate departures: a freshly-added Color node is a **true pass-through** (neutral stages are omitted, so "I haven't decided yet" costs no RTT — a fresh node emits no wrap at all), and vignette/grain ride as **fragment passes on the same shell**, never pipeline stages, because a group grade compiles with `mediaEffects: null` — the same constraint that made them fragment builtins. Inspector renders as collapsible stages in pipeline order with an active-dot per header, through the shared `InspectorSection` + `PropertyFieldList` (sections are layout around the sole renderer — no new field kind, PropertyField doctrine intact). Verified: full typecheck (shared/web/worker); `flarex:test` +14 assertions incl. the unified-vs-chain equality, no-op-when-neutral, film-passes-without-a-pipeline and the repeat-stage refusal; new `flarex-unified-color` pixel fixture **0.000%** across preview / local export / Remotion.

[x] **Flarex comp proxy — "Prepare proxy" (2026-07-27).** Fusion's render cache / Resolve's smart cache for a node comp: render the graph once over its host clip's span, then play the Edit page from that file instead of evaluating the graph every frame. Plan + slices in `plans/flarex-comp-proxy.md`. Mostly assembly — `generateSpanProxy` already renders a span through the export Worker, and `runExportCore` already lowers `flarexCompId` clips. **Invalidation is exact, not heuristic:** the key is `(container, compId, comp.version, hostLayerId, hostSignature, span, size, fps)`. `comp.version` catches every node edit and `hostSignature` catches every clip edit — the flarex hook runs at the END of the layer's draw build, so the clip's own transform/effects/trim are baked into the comp's MediaIn and a version-only key would survive a transform edit and show pre-edit pixels. That IS the "is it dirty?" question, with no flag for anyone to forget to set. **Two invariants:** the proxy is never authoritative (`export-core` and Remotion never set `flarexCompProxies`, so an export with a proxy on disk is byte-identical to one without — the render manifest stays the product contract), and it fails open to live evaluation on every miss. **Substitution is deliberately narrow:** only where nothing visual is drawn BELOW the clip for its whole span, because a rendered proxy bakes the composition background and would otherwise paint over the layers beneath. Widening that needs real alpha (`VideoEncoderConfig.alpha:"keep"`, VP8/VP9 only) and is its own slice. Edit page only — the node page must always show the live graph — plus a `?flarexProxy=0` kill switch. **Three real bugs found getting it fast, all worth remembering:** (1) the proxy rendered as webm, but the preview pool demuxes with mp4box and cannot parse Matroska, so `createFrameProvider` silently fell through to a seek-per-frame `<video>` — proxying was SLOWER than not proxying (75→35fps); comp proxies are mp4/H.264 and the container is in the key. (2) Short-circuiting the compiler does NOT stop the comp's MediaIn decoders, so a proxied comp decoded every source PLUS the proxy; the loaders are now dropped once the proxy presents its first frame. The decoders, not the graph eval, were always the dominant cost — which is also why a comp's sources visibly staggered. (3) `getFrame` returns a frame the PROVIDER closes on its next call; holding it raw handed the compositor a closed `VideoFrame`, so frames were silently discarded while the profiler read 2ms GPU. All three were invisible to existing telemetry, hence `window.__rfFlarexProxy` (mode/mime/size/decodes/nulls per comp). A wand on the clip's `fx` badge marks a clip currently playing from its proxy. **Both gates now exist, and both are mutation-verified** (`compproxy:test`, `flarex:proxy-gate`). The structural one asserts export isolation at the SOURCE level — no export path may mention `flarexCompProxies` — because that is a structural fact, and a pixel fixture could never catch someone threading the proxy into export (the fixture would render through the proxy too). The browser one measures SUBSTITUTION error, not codec loss: it feeds the live composite back in as a loss-free proxy, so the threshold is 0.5% instead of being slack enough to absorb H.264 noise, across identity/transformed/semi-transparent/blurred hosts (all 0.000%). The first structural version was WORTHLESS on its first pass — reintroducing the exact bug it existed to catch still passed it, because the host fixture was bare and had nothing to leak; it only became a gate once the host carried a blur and a content transform. **Lifecycle (S3):** a proxy that no longer matches its key was always correct-but-mute — playback fell back to live evaluation while the button still read "Prepare proxy", identical to never having built one. One `peek` (record whatever its key) now separates ready/stale/unbuilt, and stale reads "Proxy out of date" in amber with its build age. OPFS is capped at 1.5 GB, evicted oldest-first after each write and never evicting the proxy just written — these are the largest artifacts the editor writes and nothing had ever deleted one. **Deliberately not built:** S4 (background render on idle), because rendering competes for the same decoders whose contention this feature exists to remove.

[x] **Flarex — node thumbnails, and the blocked design decision resolved (2026-07-27).** Each node now shows what it outputs, Fusion/Resolve style. The block recorded below was real and is now answered the way that entry recommended: thumbnails render through **`ScenePreviewCanvas`'s own compositor** via a new `SceneViewerCaptureHandle.renderFlarexNodeThumbnail`, because a second GL context cannot sample the RenderTargets single-context preview grades media into. Sharing the hot path means inheriting its flicker history (tracker v19–v28), so it reuses that path's existing fences rather than inventing new ones: a hard `isPlaying` refusal (the v24 capture-race rule), the `spec.width !== this.width` guard that stops an offscreen render from resizing — and thereby clearing — the visible canvas, and `requestDraw()` afterwards because a thumbnail necessarily overwrites the retained composite the color scopes sample. The comp is re-rooted per node with `flarexPreviewRootNodeId` (never touching the user's view dot), and deliberately WITHOUT `flarexCompProxies` — a comp proxy replaces the whole lowering, so every node would have thumbnailed identically as the comp's final output. **Cost, which was the user's condition on the feature:** new `SceneCompositor.renderFrameThumbnail` composites at the compositor's size but blits down BEFORE readback, so a node costs ~20KB across the bus instead of a 33MB full-frame `readPixels` GPU drain; work is scheduled only on `requestIdleCallback`, only for nodes inside the viewport (centre-out), at most one per idle slice, and cached on the node's ADR-009 content hash — so a static graph renders each visible node once and then costs nothing, and an edit invalidates exactly the edited node plus everything downstream of it. **Node presentation redesigned to the Resolve idiom** in the same pass (the previous layout read as a wide label bar with an inset picture): a picture node is now a fixed tile — image in a thin bezel, then a footer carrying the node's creation-order index and status glyphs (view dot, keyframed diamond, disabled bar) — with the NAME drawn OUTSIDE, above the tile. Without a picture the node keeps the compact Fusion form, name inside; that split is the rule both references follow. Socket banks are now CENTRED on the picture band and each bank centres on its own count, so a 1-in/1-out node has both dots on the centre line instead of bunched under the top edge. **Accent doctrine enforced on the graph:** wires and sockets were painted from fixed `--flarex-socket-*` hues (blue/green/amber) that were theme-independent by design — which is precisely what made the graph look off-brand, since it stayed those colors through every accent change. Both now draw in the app accent (resting wire at 0.42, selection/splice at 0.95), and the DATA TYPE is carried by treatment rather than hue: image = solid disc, matte = hollow ring, number = small dot, all circular. Those three CSS vars are deleted. Geometry invariants asserted: sockets stay inside the picture band and never the footer, the footer fills the tile, chrome nodes (backdrop/group/reroute) get no picture and no index, and the fit-view bounds include the outside label's headroom. Toggle in the Flarex toolbar, persisted, default on. Verified: full typecheck; `flarex:test`, `flarex:align:test` (+22 geometry assertions), clipboard + proxy-eligibility green; 11/11 Flarex pixel fixtures at the floor — re-run after the sibling agent's ADR-008 cache commit (6a7ccd3), which touches the same compositor this renders through, with identical results.

[x] **Flarex — the host froze and the loaders played: decoder-pool mode isolation (2026-07-27).** The exact inverse of the 2026-07-26 freeze, and the tell was one clause in the report: *"host even dont update when paused."* A stalled clock still updates on scrub (pausing re-enables the memo's time compare), so a source dead while PAUSED is a dead decode, not a lagging one — that ruled out the whole previous class on sight. **Cause 1, mode-blind warm reuse:** the preview pool matched parked providers by URL alone. A comp routinely loads one file as BOTH the host clip and a MediaIn source; the loader creates a **software** decoder for it (the 07-26 contention fix), parks it on release, and the host warm-reused it. The host is lag-INtolerant by design, so a software decode of a full-res source blew past `WC_HOLD_LAG_S` → freeze-hold → sustained-hold bail → `wcBailedSources` → native `<video>` for the session. The mirror leak is equally bad: a loader inheriting the host's hardware provider is back on the contended block. **Cause 2, software sessions charged to the hardware cap:** `MAX_WC_SESSIONS = 3` models the GPU's video block, but software decoders occupy none of it — host + 2 loaders filled all 3, and whoever acquired last was refused a session. Loaders are immune to that fallback (`tolerateLag`: never freeze-hold, never bail, never go native), so **the loser was structurally guaranteed to be the host**: the previous fix made loaders unstarvable without giving the host any protection. **Fix:** warm reuse matches `(url, software)`, lifted to a pure exported `findWarmIdleIndex` because a mode-mismatched reuse is otherwise invisible (it counts as a healthy cache HIT); hardware and software get separate counts, caps (3 / 4), idle pools, eviction and preemption victims, so no number of loaders can refuse the host a slot; new `window.__rfWcMode` reports per source which path it ACTUALLY took (`wc-hw`/`wc-sw`/`element`) — unanswerable from the console before, and both freezes were mis-diagnosed for rounds without it. New gate `pnpm --filter @orreris/web wcpool:test` (22 assertions, mutation-verified: a URL-only match fails exactly the 3 mode-mismatch assertions). **Rule:** when a fix makes one class of source unstarvable, ask which source is now guaranteed to lose — immunity is redistributed, not free. Verified: full repo typecheck. Not committed.

[x] **Flarex evaluation engine — Slice 2 COMPLETE: content-addressed cache made correct + bounded (commit 3c, 2026-07-26).** Commits 1/2/3a/3b had landed the cache; 3c closes it, and closing it turned up a **live correctness bug in 3b**, not just the missing eviction that commit flagged. (**3c-A — stale artifacts.** The cache identity did not describe the pixels: dependencies were harvested from fragment passes ONLY (`collectDrawDependencies`), so a subtree whose sole dynamic input was live media declared nothing and keyed identically every frame. The compositor's hit path composites the cached artifact and *skips the children render outright*, so a `MediaIn` fanned out to 2+ consumers — routine Fusion wiring, materialized by `fanout > 1` — served its first decoded frame **forever**: a permanently frozen clip. Added a 96MB GPU budget + 64-entry cap with **segmented LRU**: probation drains before protected, so the stream of single-use per-frame artifacts cannot flush the ones with proven cross-frame reuse. The policy is extracted as a pure `planArtifactEviction` (GL-free, unit-tested), and it distinguishes volatile from durable artifacts *empirically* — "was it actually reused?" — so the compositor still never interprets a dependency's name. `contentCacheStats()` exposes hits/misses/promotions/evictions/bytes as the reuse scorecard. **3c-C — the gate that was missing.** `render:compare:pixels` renders ONE frame per fixture, so it is structurally blind to cross-frame cache bugs — which is exactly why 3b's staleness shipped past all 8 Flarex fixtures. New `pnpm --filter @orreris/worker flarex:cache-gate` renders a SEQUENCE two ways — one long-lived compositor (warm cache) vs a fresh compositor per frame (cold oracle) — and asserts per-frame equality, that the picture actually advances, that memory stays in budget, and that a static comp genuinely reuses (a cache that never hits is trivially parity-clean and worthless). **Mutation-verified**: reverting 3c-A makes the gate fail with *"warm sweep produced ONE distinct frame while cold produced 24 — the picture is frozen."*) Verified: shared/web/worker typecheck green; `flarex:test` +17 assertions green; all 49 `render:compare:pixels` fixtures at the floor. ## Orreris AI Operating System — Phased Roadmap

Vision (`AI_ARCHITECTURE.md`): Orreris is a professional editor with an **AI operating system on top** — "Claude Code for video editing". AI never mutates the timeline directly. It *plans → selects registered tools/actions → previews → asks when it matters → executes through an approved registry*, leaving everything editable and undoable. The editor stays fully usable without AI.

```text
User → AI Chat Panel → Planner → Capability Registry → Plan Review
     → Executor → Timeline Action Registry → patches → Undo Stack → Editor Timeline
```

Foundational rule: the **Timeline Action Registry is the only approved mechanism for AI timeline mutation.** AI may only invoke registered, validated, reversible actions that *wrap* the existing pure ops — never touch `TimelineLayer`/effects/keyframes directly, never touch rendering (manifest stays the contract; web↔Remotion parity preserved).

### Provider Gateway — multi-model failover (free-first, internet-scale)

Decision (validated for an indie launch): don't bind the brain to one provider. Behind the *unchanged* `/api/ai/plan` route, swap the single LLM call for a **config-driven pool with automatic failover**. The full AI spine (PlannerProvider, slice payload, **registry validation of every step**, Plan Review, Executor→patches→Undo, permission modes, memory, analytics, interactive clarify/tool loop) is untouched — only the server-side brain grows. Keys stay server-side (multi-user safe). Reasoning models are weaker than Claude, but **registry validation + deterministic floor** guarantee safety/precision regardless of model quality.

```text
Cerebras → Groq → OpenRouter → Gemini → Claude Sonnet (paid, opt-in) → Deterministic planner (always-free floor)
```
